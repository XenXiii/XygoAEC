# Tenant File Storage Operations Runbook

This runbook defines the staging/production object-storage contract for Xygo report photos,
attachments, and evidence files. The implementation supports private S3-compatible storage and a
local development adapter. This document does not create a bucket, install credentials, validate a
provider account, or deploy the application.

## Security invariants

- Production and staging deployment manifests use `XYGO_STORAGE_DRIVER=s3`. The `local` driver is
  for developer/test data only and is rejected by the production configuration gate.
- The bucket is private. `XYGO_STORAGE_PUBLIC_ACCESS=blocked` is required, and the provider's account-
  and bucket-level public-access-block evidence must be attached to the deployment record. Never use
  object ACLs or a public website endpoint.
- Object keys are generated by the API under an internal tenant-hashed `tenants/.../files/...` prefix.
  Clients cannot supply a bucket, key, path, or tenant prefix.
- API authorization checks the PostgreSQL file record's tenant before list, upload completion,
  download, overwrite, or delete. Object-storage keys and credentials are never returned in file
  metadata or `/runtime-config.json`. A presigned URL necessarily contains its single-object path and
  provider credential identifier, but never the secret access key and never grants bucket listing.
- S3-compatible uploads and downloads use short-lived presigned targets. Upload signatures bind the
  object key, declared byte length, create-only `If-None-Match: *`, AES256 encryption header, and tenant metadata. Completion performs
  a HEAD check for tenant metadata, exact MIME type, and exact size before the record becomes `ready`.
- The local adapter is an authenticated API proxy. It writes mode-0600 object/metadata files below a
  fixed root and rejects keys that escape that root.
- Allowed MIME types are explicit; wildcards, HTML, SVG, scripts, and executables are not accepted by
  the example policy. `report_photo` additionally requires an allowed image MIME type.
- Client viewers see only `ready` records explicitly marked client-visible. A report file cannot be
  client-visible through staff action unless its linked report is already approved.

## Required private runtime settings

Set the following only on API/worker server processes through the approved secret/config manager:

- `XYGO_STORAGE_DRIVER=s3`
- `XYGO_STORAGE_BUCKET`: private bucket name
- `XYGO_STORAGE_REGION`: provider region
- `XYGO_STORAGE_ENDPOINT`: private HTTPS S3-compatible API endpoint; never a website endpoint
- `XYGO_STORAGE_ACCESS_KEY_ID` and `XYGO_STORAGE_SECRET_ACCESS_KEY`: short-lived or rotated runtime
  credentials; never browser configuration
- `XYGO_STORAGE_FORCE_PATH_STYLE`: provider compatibility flag (`false` for AWS S3)
- `XYGO_STORAGE_PUBLIC_ACCESS=blocked`
- `XYGO_STORAGE_SERVER_SIDE_ENCRYPTION=AES256`
- `XYGO_STORAGE_MAX_FILE_BYTES`: 1 KiB through 250 MiB; the example uses 25 MiB
- `XYGO_STORAGE_ALLOWED_MIME_TYPES`: explicit comma-separated allowlist without wildcards
- `XYGO_STORAGE_SIGNED_URL_TTL_SEC`: 60–900 seconds; the example uses 300
- `XYGO_STORAGE_RETENTION_DAYS`: 1–3650 days; the example uses 365

`XYGO_STORAGE_LOCAL_ROOT` is local-development-only. Do not mount the local adapter in staging or
production. Storage settings are server-only and are regression-tested out of public web runtime
configuration.

## S3-compatible staging setup

1. Create a dedicated staging bucket in the approved region. Enable provider account- and bucket-level
   public-access blocking, ownership enforcement, TLS-only access, server-side AES256 encryption,
   versioning, access logging, and deletion protection where supported.
2. Create a least-privilege runtime identity limited to `PutObject`, `GetObject`, `HeadObject`, and
   `DeleteObject` for `<bucket>/tenants/*`. Do not grant bucket policy, ACL, public-access, lifecycle,
   or unrelated bucket administration permissions to the application identity.
3. Configure CORS for the exact HTTPS web application origin only. Allow required `PUT`, `GET`, and
   `HEAD` methods and the `content-type`, `content-length`, `if-none-match`, `x-amz-server-side-encryption`, and
   `x-amz-meta-xygo-tenant-id` headers. Never use `*` origins or expose credentials.
4. Configure lifecycle/version retention to meet the approved `XYGO_STORAGE_RETENTION_DAYS`, legal
   hold, and deletion requirements. Version expiration must not be shorter than the database/audit
   retention period.
5. Bind the settings above to API/worker server processes. Do not inject them into the web process,
   browser bundle, build arguments, logs, or pull-request variables.
6. Run the production configuration tests against the manifest without printing secrets. Start the
   API only after PostgreSQL migration `0004_tenant_file_storage` is applied and readiness passes.
7. Run an isolated smoke flow: create an upload intent, upload a permitted test image, complete it,
   download it as the owning tenant, prove a second tenant receives denial, delete it, and verify both
   `api.file.upload_completed` and `api.file.deleted` audit events.
8. Record bucket/region identifiers, public-access-block evidence, IAM policy review, encryption,
   versioning/lifecycle status, CORS policy, smoke-test result, owner, and rollback decision window.

## Upload, completion, and cleanup states

- `pending_upload`: metadata exists but the object is not yet trusted. A missing object is safe and the
  completion call remains retryable. Periodically identify expired pending records and remove any
  matching orphan object after the retention owner approves cleanup.
- `ready`: object tenant metadata, MIME type, and byte length matched the upload intent; metadata and
  `api.file.upload_completed` evidence committed atomically in PostgreSQL.
- `deleting`: the database recorded deletion intent before object removal. Retrying DELETE is safe and
  completes metadata/audit finalization after object deletion.
- `deleted`: object removal completed, access is denied, and soft-deleted metadata/audit evidence is
  retained. Never reuse the object key or file ID.

Overwriting a `ready` object through the API is denied. A replacement is a new file record/object,
which preserves the old evidence trail and makes rollback reviewable.

## Backup, retention, and restore

- PostgreSQL backup/PITR protects file metadata and audit links; object-store versioning protects the
  bytes. Neither is a substitute for the other. Align both retention windows and record their owners.
- Monitor failed replication/versioning, lifecycle deletions, unusual download/delete volume, storage
  capacity, 4xx signature failures, and file records stuck in `pending_upload` or `deleting`.
- For a restore drill, restore PostgreSQL into an isolated database and restore/copy the matching
  object versions into an isolated private bucket. Bind temporary verification credentials without
  printing them.
- Verify migration/readiness, compare tenant/project/report/file counts, sample checksums, confirm
  every sampled `ready` record has a same-tenant object, and prove cross-tenant download denial.
- Record achieved RTO/RPO, missing/orphan counts, object-version timestamps, audit verification, and
  corrective work. Do not approve staging until a timed combined database/object restore succeeds.

## Incident handling

- Suspected public exposure: block bucket access at the provider, revoke signing credentials, disable
  upload/download traffic, preserve access logs, identify affected keys/tenants, and notify the incident
  owner. Do not delete evidence during triage.
- Credential leak: revoke/rotate the object-store identity, restart affected server processes, inspect
  provider access logs and presigned activity, and verify no public policy or unauthorized object was
  created.
- Metadata/object mismatch: stop completion/download for the affected record, preserve the object
  version, compare tenant metadata/MIME/size/checksum, and create a new record rather than overwriting
  audit history.
- Malware or prohibited content: this slice rejects unsafe declared MIME types but does not implement
  malware scanning/quarantine. Block the record/object, preserve incident evidence, and keep staging
  approval blocked until the worker/quarantine path exists.

## Rollback

Migration `0004_tenant_file_storage` is additive. Roll back application code only if the prior release
remains compatible with the forward schema; do not drop the table during an incident. Disable new
upload intents before rollback, let in-flight presigned URLs expire, and retain private objects plus
metadata for reconciliation. If object configuration is faulty, restore the prior secret binding and
restart the API without changing bucket publicity or deleting objects. Resume traffic only after
PostgreSQL readiness, private-bucket evidence, owning-tenant download, cross-tenant denial, and audit
verification all pass.
